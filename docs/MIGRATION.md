## 我理解的实验目标

被试执行一个有持续认知负荷的主任务，在过程中通过眼镜接收简短通知。我们关心通知是否被理解，以及通知出现前后主任务表现如何变化；任务结束后再收集理解题和主观评价。程序应保留足够的原始数据，后续能重算，而不是只保存一个正确率。

这延续了原程序的“电脑主任务＋眼镜通知＋后台控制”，主要变化是把静态工作场景任务换成连续 2-back。A1 的通知材料可以关注行数和内容负荷；实际操纵和分组要由材料确定。三份参考没有完整定义 A2，也没有给出可直接执行的移动主任务，不能从目录名推断它们已明确。

## 建议第一版做成什么

电脑打开 `/admin`，手机扫码进入同一后台。主试选择匿名编号和一份计划，在电脑手动打开被试页。被试页先完成规则说明、声音检查和练习，再进入正式任务。手机用于监看和记录，音频调度与反应采集始终在被试电脑完成。

一次任务的大致流程：

```text
说明与声音检查 → 2-back练习 → 正式任务

通知任务：准备 → 2-back基线
                  ↓ 眼镜通知显示8.5秒，2-back继续
                2-back观察窗口 → 完整刺激/反应步结束
                → 理解题 → 简短评价 → 保存 → 休息/下一任务

对照任务：相同主任务时序与虚拟通知锚点
          → 不发送眼镜文字 → 不问通知理解题
          → 通用评价 → 保存 → 休息/下一任务
```

对照组不问“消息理解难度”这类没有对象的问题。若采用两份短评价，题干与适用对象写在配置中，例如通用努力对所有任务适用、通知干扰对通知任务适用；不要把 Word 的两道消息评价原样套进 sham。

第一步只用几条明确标为 synthetic 的调试材料打通链路，随后接入真实材料。12＋4 可以成为某份正式计划，但不为了实现这个数字先制造调度框架。练习与正式使用相同主任务实现，数据以 practice/formal 区分。

## 真正需要新写的部分

### 连续 2-back 运行器

每次任务开始前由随机种子生成完整刺激序列、目标标记和计划时间，固定保存。匹配判定由内容与前两项比较得到，前两项不评分；目标比例、刺激集合、双键/单键规则在配置中明确。不要边播放边重新生成下一项。

被试端预加载音频，使用 Web Audio 的时间轴提前安排播放。监听 keydown，在异步请求之前记录按键时间、repeat 标志、当前刺激和原始按键；首次有效响应判分，其他按键仍作为事件保留。匹配和不匹配双键映射写入实际快照，不复用 SH 表单提交作为每个刺激的按键接口。

后台负责计划、会话状态和最终校验，被试端负责音频与按键的精细时间线。不能每个声音都等一轮 HTTP 请求，也不能使用现有每秒 tick 或页面轮询推动 2-back。短批次上传原始事件、保存上传游标、按 event_id 去重；独立采集与后台表单轮询解耦，避免渲染重置音频。

预排音频时间是软件调度证据，不能直接称为真实听到的时间。保存 AudioContext 时间、浏览器 performance 时间的映射与可用的输出时间信息、输出延迟诊断。声学起点、按键设备延迟和显示光学起点需另做设备验收；不凭代码承诺 ≤10 ms 精度。

### 任务状态和数据模型

新任务用 session → block → trial_attempt → primary_item 表达。明确区分 Word 中“大Trial”和 2-back 中的一个刺激步，避免两者都叫 trial 却共用一个编号。

建议正式任务状态为 READY → RUNNING → PROBE → RATING → BREAK → COMPLETED。RUNNING 内保存通知和 sham 的子状态，不因通知出现而暂停主任务。通知等待发送、已接受、双眼已绘制、已消失、失败分开保存。

现有 interventions 主键是 `(session_id, stage_id)`，不适合多次任务和重跑。新通知应按 request_id 唯一，明确关联 trial_attempt_id；恢复和重跑必须生成新的尝试身份。逐刺激记录保留 stimulus_index、is_target、响应、RT、超时和有效性，原始按键单独保留。

旧 SH 的暂停是页面冻结并允许恢复；新连续任务在中途暂停会改变条件。推荐正常暂停只在任务边界生效，任务内紧急停止则保留 partial/invalid，恢复到下一合法边界，不能补播中断期间音频或假装连续完成。

### 眼镜通知与三套时钟

当前 Android 和 TypeScript 都把固定模式的 `duration_ms` 限制为 8500，Android 清屏也明确加 8500。首轮沿用它即可；若正式要求 8000 或其他时长，必须同步修改协议校验、Android 计时、去重指纹、Mock 和导出，而不是只改一个 JSON 数字。

现有三模式为 legacy_8500、tone_8500、confirm_until_ack。连续听觉任务第一版只使用 legacy_8500：tone 会引入额外听觉刺激，confirm 会改变曝光时长。后台手动通知和主试跳题在正式 RUNNING 期间应禁用或触发整次任务无效，不能继续混作正式数据。

眼镜已有 drawn/hidden/clock_id，但服务器每秒回收设备事件。轮询到达时间不是实际出现时间，也不能用“服务器收到 hidden 后再数50秒”冒充实际消失后50秒。需要较及时的回收/推送，以及电脑与设备时钟的映射和误差记录。

建议通过相同 USB socket 加入轻量时钟交换，保存电脑发送/接收时刻与眼镜 uptime，估计偏移和往返不确定度；浏览器 performance、音频时间、服务器单调时间也保留映射。没有可靠映射时仍可运行调试并记录原始证据，但不能产出看似确定的跨设备 Pre/During/Post。重连、clock_id 变化或回执迟到应打 QC 标记。

已有双眼绘制回调是应用证据，不等于光学出光。保持这个表述，映射不能把证据性质升级为光学测量。

### 材料行数和视觉设置

复用当前样式作为起点：27 PPD、0.6° 字号、Medium 500、字距 2%、9.55° 最大文本宽、0.5° 内边距、白色文字和35%遮罩、窗口亮度 1/6。亮度约1000 nits是以6000 nits为前提的线性假设，不是实测值。

材料记录 text_lines、预期行数、实际文字、编码版本、内容单元、问题与答案。发送前核对设备实际布局，溢出或实际行数不符则阻止该材料进入正式任务；不自动缩小字号凑行数。当前 MessageView 能固定字号和显式换行，但还不是“一定只渲染指定1/2行”的严格验证器，需要补限制和布局元数据对比。

## 推荐落地顺序

1. **基线搬迁和需求提取（本次完成）**：保留可对照源代码、原始参考和来源提交；列清核心差异与改造点。
2. **单电脑 Mock 端到端**：新增 A1 工作区；听觉2-back、双键响应、无声8.5秒模拟通知、sham、理解题、固定短评价、事件落盘和导出；先用少量调试材料。
3. **复用真机链路**：保持当前显示方式，补布局验证、及时事件回收和时钟交换；完成一条通知与一条 sham 的端到端采集。
4. **接入真实材料与正式计划**：锁定行数、内容编码、问题、音频、时序和评价，生成可重现计划；再考虑是否采用12＋4。
5. **Pilot后扩展**：决定要不要调时长、加自由复述、RTLX、移动主任务和 A2；依据实际数据与研究决策增加，不因参考列了就预先实现。

后续用户明确要求测试或验收时，优先覆盖：通知期间声音不中断；sham 不发眼镜也不提问；双键首响应和冗余按键留存；同种子计划一致；设备迟到回执不被当作真实起点；失焦/断联保留无效尝试；崩溃后不悄悄重播；从原始事件重算导出一致。此处是验收计划，本次没有执行。

## 现阶段缺的输入

- 真实通知正文、指定换行、正确答案及选项、材料来源/编码；三份文档没有提供完整材料表。
- 听觉2-back的音频资产、刺激集合、固定音量及输出设备。可以先做合成调试，但正式素材不能由工程默默编造。
- A1正式操纵到底是行数、内容单元或两者，以及控制条件和分配规则。
- Q2/Q4的明确含义及移动任务是否已有设备/程序；A2的实际任务和研究变量。

这些不阻碍先搭建 Mock 链路；在真实材料和研究变量确认前，不把候选参数写成已冻结规范。
